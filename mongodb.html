DOCUMENT
Tudo entre { }. É o registro — a “linha” da tabela, só que com estrutura.
_id
A chave primária. Obrigatório e único na collection. Não mandou? O Mongo gera.
FIELD (campo)
O nome antes dos dois-pontos. É a “coluna”.
VALUE (valor)
O que vem depois dos dois-pontos.
TIPOS BSON
Cada valor tem um tipo de verdade: string, int, bool, date, decimal, ObjectId…
SUBDOCUMENTO
Documento dentro do documento. Acessa com "endereco.cidade" (dot notation).
ARRAY
Lista de valores. { tags: "gamer" } já procura dentro da lista.
ARRAY DE DOCUMENTOS
Lista de objetos. É o “embutir” que a gente vê no fim.
O DOCUMENTO INTEIRO
Máx. 16 MB por documento. O próximo cliente pode ter outros campos.
Mesmo problema, outro nome.

02 · Alteração · todo update tem duas partes
mongosh
db.pedidos.updateOne(
  { _id: 1042 },                 // FILTRO

)
updateOne: altera no máximo 1 documento — o primeiro que bater.
Parte 1 · filtro: igual ao WHERE. Quem vai mudar?
Parte 2 · operador: o que muda. $set define o valor do campo.
Esqueceu o operador? O mongosh recusa: Update document requires atomic operators.
Pagamento aprovado → status: "pago"
matchedCount: 1 → achou. modifiedCount: 1 → mudou.
De novo? matched 1, modified 0: já estava “pago”, nada foi regravado.

A correção · deixa o banco fazer a conta
mongosh
db.produtos.updateOne(
  { _id: "SKU-102", estoque: { $gte: 1 } },
  { $inc: { estoque: -1 } }
)
O filtro só acha o produto se ainda tiver estoque ($gte = maior ou igual).
$inc soma no próprio banco (aqui, −1). Ninguém lê antes.
Filtro + alteração acontecem juntos, atomicamente, no documento.
O resultado diz quem ganhou: modifiedCount 1 = vendeu · 0 = esgotado.
A corrida, agora do jeito certo
modifiedCount: 1 → Cliente A levou. Estoque 0.
matchedCount: 0 → filtro não achou ninguém. Tela mostra “Esgotado”. Nunca −1.

A correção · checkout dentro de uma transação
mongosh
const s = db.getMongo().startSession()
const loja = s.getDatabase("loja")
s.startTransaction()
try {
  const r = loja.produtos.updateOne(
    { _id: "SKU-102", estoque: { $gte: 1 } },
    { $inc: { estoque: -1 } })
  if (!r.modifiedCount) throw new Error("Esgotado")
  loja.pedidos.insertOne({ cliente_id: 7 })
  s.commitTransaction()
} catch (e) {
  s.abortTransaction()
}
Sessão: o “canal” que agrupa as operações.
As collections são acessadas pela sessão, senão ficam fora da transação.
startTransaction: daqui pra baixo, nada é definitivo ainda.
Baixa o estoque, com a mesma proteção da Air Fryer.
Esgotado? throw → pula direto pro catch.
Cria o pedido — em outra collection, na mesma transação.
commitTransaction: agora as mudanças valem, todas juntas.
Qualquer erro? abortTransaction desfaz tudo.
Transação custa mais que um update simples: use quando várias escritas precisam andar juntas.
O mesmo carrinho, com transação
s e loja já estão prontos, iguais às 2 primeiras linhas do slide anterior.
Transação aberta. Daqui pra frente, nada é definitivo.
Fone: 37 → 35… por enquanto.
Air Fryer: matchedCount: 0 → esgotada. A API cai no catch…
O Fone voltou pra 37. Nada aconteceu pela metade. ✅ Se tudo desse certo: commitTransaction().

A correção · update + insert = upsert
mongosh
db.pagamentos.updateOne(
  { _id: "evt_9f3a" },
  { $set: { status: "aprovado" },
    $inc: { avisos: 1 } },

Achou → atualiza. $inc só pra gente contar quantos avisos chegaram.
upsert: true → não achou? Cria, usando o _id do filtro + os campos do update.
1 aviso ou 10, o mesmo estado final. Isso tem nome: idempotência.
Chegou o webhook 📩
Não existia → upsertedCount: 1. Criou com o _id do filtro.

A correção · regra na porta da coleção
mongosh
db.createCollection("pedidos", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["cliente_id", "total", "status"],
    properties: {
      total:  { bsonType: "decimal" },
      status: { enum: ["pendente", "pago",
                       "enviado"] },
      itens:  { bsonType: "array",
                minItems: 1 }
    }
  }}
})
Cria a coleção já com regra.
validator + $jsonSchema: o padrão JSON Schema, com tipos BSON.
required: faltou um desses? Nem entra.
total tem que ser decimal. “59,90” em texto é barrado.
enum: só esses valores. Adeus “Pago”, “PAGO”, “pagou”.
Não é obrigatório, mas se vier itens, tem que ser lista com 1+ item.
Tentando de novo, agora com regra
Barrado na porta: total veio como texto.
“Pago” com P maiúsculo? O enum não aceita.
Agora sim. O banco protegeu o relatório de amanhã.
E se a coleção já tem 2 milhões de pedidos fora da regra?
validationAction
error → bloqueia o inválido.
warn → deixa entrar, só registra no log.
validationLevel
strict → valida todo insert e update.
moderate → não cobra de quem já era inválido.
Padrão: strict + error.

Apertar a regra sem derrubar a loja

Mudando a regra de uma coleção que já existe
mongosh
db.runCommand({
  collMod: "pedidos",
  validator: { $jsonSchema: { required: ["total"] } },
  validationLevel: "moderate",
  validationAction: "warn"
})
collMod = collection modify. Sem recriar, sem perder dado.
O validator novo substitui o anterior inteiro.
moderate: documentos antigos inválidos não travam updates.
warn: não bloqueia nada, só registra no log. Zero downtime.
moderate na prática
Regra nova: total decimal. O pedido 900 é antigo e já está fora dela.
Já era inválido → moderate deixa o update passar. A operação não trava.
Um documento válido não pode virar inválido. Erro.
Como você lê decide como você guarda.
Embutir
Documento dentro do documento. Lido sempre junto.

Referenciar
Guarda só o _id do outro. Dado compartilhado ou que cresce sem fim.

1 · Update sem operador→ “Update document requires atomic operators”
updateOne({ _id: "SKU-101" }, { estoque: 10 })
updateOne({ _id: "SKU-101" }, { $set: { estoque: 10 } })
2 · Buscar _id como texto→ volta vazio, “mas o id existe!”
find({ _id: "65f1c2a9e4b0a1b2c3d4e5f6" })
find({ _id: ObjectId("65f1c2a9e4b0a1b2c3d4e5f6") })
3 · $set no subdocumento inteiro→ o “uf” sumiu
$set: { endereco: { cidade: "Recife" } }
$set: { "endereco.cidade": "Recife" }
4 · updateOne achando que muda todos→ modifiedCount: 1
updateOne({}, { $set: { promo: true } })
updateMany({}, { $set: { promo: true } })
🚫 Mais 4 pegadinhas
5 · Chave repetida no filtro→ o JavaScript fica só com a última
find({ preco: { $gt: 50 }, preco: { $lt: 100 } })
find({ preco: { $gt: 50, $lt: 100 } })
6 · Número entre aspas→ texto só compara com texto: volta vazio
find({ estoque: { $gt: "10" } })
find({ estoque: { $gt: 10 } })
7 · $push com array→ vira array dentro de array
$push: { tags: ["bf", "promo"] }
$push: { tags: { $each: ["bf", "promo"] } }
8 · null também acha quem não tem o campo→ traz a mais
find({ telefone: null })
find({ telefone: { $exists: false } })
